> 토비의 "클로드 코드와 스프링 개발하기" 3회 시리즈 통합 학습 자료
> 이 자료는 개별 강의 가이드를 대체하는 것이 아니라, **시리즈 전체를 관통하는 레퍼런스**입니다.
> 개별 강의 시청 시에는 각 회차별 학습 가이드를 함께 보세요.

## 2. 에이전틱 프로그래밍 통합 원칙 10선

3회 강의에서 추출한 20개 원칙을 중복 제거하고 10개로 통합했습니다.

### 원칙 1: 에이전틱 루프를 이해하라

> 출처: 2회차 | 카테고리: 기반 지식

클로드 코드의 동작 원리(컨텍스트 → 액션 → 검증 → 반복)를 이해해야 문제를 진단하고 AI에 개입할 수 있다. 화면에서 도구 아이콘이 깜빡일 때 "지금 어떤 도구를 쓰라고 한 건지" 의식하라.

- **왜**: 원리를 모르면 AI가 왜 그렇게 행동하는지 이해 못 하고, 교정도 못 함
- **실전 예시**: Explore 에이전트를 쓰면 더 좋은 분석이 나오는데, AI가 Glob/Grep만 쓰고 있다면 "Explore를 사용하라"고 명시적으로 지시

### 원칙 2: 계획에 시간을 투자하라

> 출처: 1회차 + 3회차 | 카테고리: 워크플로우

**탐색 → 계획 → 구현 → 커밋** 4단계를 항상 따르라. "만들어줘" 한 방은 별로인 결과를 낳는다. 잘하는 사람은 1시간 반 중 1시간을 계획에 쓴다.

- **왜**: 준비 없이 구현하면 잘못된 방향의 코드가 대량 생성됨. 되돌리는 비용 > 계획하는 비용
- **실전 예시**: 플랜 모드에서 AI의 계획을 먼저 확인 → 버전/기술 선택이 올바른지 검증 → 교정 후 구현

### 원칙 3: AI에게 먼저 시키고, 결과를 교정하라

> 출처: 1회차 | 카테고리: 코드 품질

AI의 디폴트 행동을 먼저 관찰해야 "무엇을 교정할지" 알 수 있다. 선행 지시를 과도하게 하면 오히려 AI 능력을 제한한다.

- **왜**: AI가 이미 잘하는 것까지 지시하면 불필요한 제약이 됨. 못하는 것만 정확히 교정하는 것이 효율적
- **실전 예시**: 서비스 코드를 먼저 생성하게 한 후 → 생성자 주입, 트랜잭션 패턴은 잘했는지 확인 → Mock 테스트를 통합 테스트로 교정

### 원칙 4: CLAUDE.md에는 AI가 못하는 것만 넣어라

> 출처: 1회차 | 카테고리: 코드 품질

AI가 이미 잘하는 것까지 넣으면 파일이 비대해지고, 정작 중요한 지시를 AI가 무시한다. 대화에서 발견된 "교정이 필요한 것"만 선별적으로 기록하라.

- **왜**: 과잉 지시 → CLAUDE.md 비대화 → 성능 저하. "엔티티에 @Entity 붙여라" 같은 건 불필요
- **실전 예시**: "도메인 테스트는 순수 단위 테스트, JPA 사용 금지" (O) / "패키지 이름은 com.으로 시작" (X, 이미 잘함)

### 원칙 5: 3번 반복하면 스킬로, 맥락 불필요하면 에이전트로

> 출처: 2회차 + 3회차 | 카테고리: 도구 구축

반복되는 프롬프트는 스킬로 만들어라. 결과만 필요하고 대화 맥락이 불필요한 작업은 서브 에이전트로 분리해서 컨텍스트를 보호하라.

- **왜**: 스킬 = 함수 추출과 같은 원리. 에이전트 = 컨텍스트 오염 방지
- **판단 기준**: "이후 대화에 맥락이 남아야 하는가?" → Yes: 스킬 / No: 에이전트
- **실전 예시**: 프로젝트 생성 → 스킬. 코드 품질 분석 → 에이전트

### 원칙 6: 스킬은 워크플로우 + 레퍼런스 두 가지로 활용하라

> 출처: 3회차 | 카테고리: 도구 구축

스킬은 반복 작업 자동화뿐 아니라, AI가 모르는 지식(최신 기술 변경점, 팀 관례)을 저장하는 레퍼런스 용도로도 활용하라.

- **왜**: AI 모델의 학습 데이터에는 최신 정보가 없고, 팀만의 관례는 아예 모름
- **실전 예시**: "스프링부트 4 변경점" 스킬 → 개발 시 자동 참조. "카프카 사용법" 스킬 → 웹 학습 후 지식 보존

### 원칙 7: 플러그인은 선별적으로, 기본 도구부터 파악하라

> 출처: 2회차 | 카테고리: 환경 설정

"에이전트 150개, 스킬 1500개" 설치는 재앙. 기본 도구(Bash, Read, Write, Grep 등)만으로 대부분의 작업이 가능하다. 남의 도구를 통째로 가져오지 말고, 필요에 의해 하나씩 추가하라.

- **왜**: 도구 목록이 매번 컨텍스트에 포함됨 → 많이 설치하면 성능 저하 + 제어 불능
- **실전 예시**: 시작 시 오피셜 플러그인에서 4개만(Ralph Loop, Skill Creator, Exploratory Output Style, Plugin Dev) → 나머지는 필요할 때

### 원칙 8: 컨텍스트를 관리하라

> 출처: 2회차 + 3회차 | 카테고리: 성능 최적화

대화 히스토리가 길어지면 AI 성능이 떨어진다. 200K~300K 수준에서 끊고, 문서가 충분히 만들어진 상태에서 새 세션으로 이어가라.

- **왜**: 앞에서 했던 모든 대화가 뒤의 간단한 요청에도 함께 날아감 → AI가 집중 못함
- **실전 예시**: `/context`로 사용량 확인 → 200K 넘으면 문서화 후 클리어 → 새 세션 시작

### 원칙 9: 멀티 모델로 검증하라

> 출처: 3회차 | 카테고리: 품질 보증

클로드가 셀프 리뷰해도 놓치는 것을 Codex/Gemini가 잡아낸다. 설계 리뷰, 코드 리뷰 시 다른 모델의 관점을 활용하라.

- **왜**: 같은 모델의 셀프 리뷰는 같은 편향을 가짐. 다른 모델은 다른 관점에서 지적
- **실전 예시**: 설계 완료 → Codex 리뷰("스프링 4 기능을 오해했다") → Gemini 리뷰 → 컨센서스 분석 → 반영

### 원칙 10: 한 달에 한 번 리셋하고, 모델 업데이트 시 재검증하라

> 출처: 1회차 + 3회차 | 카테고리: 지속적 개선

설정/스킬이 쌓이면 오히려 성능이 떨어진다. 확신 있는 것만 다시 빌드업하라. 새 모델이 나오면 기존 스킬의 유효성을 재검증하라.

- **왜**: 옛날 모델용 스킬이 새 모델에서는 불필요하거나 역효과를 낼 수 있음
- **실전 예시**: 새 모델 출시 → 레퍼런스 프로젝트에서 스킬 없이 테스트 → 여전히 필요한 것만 복원

## 3. 에이전틱 개발자 스킬 트리

### Level 1: 입문 (1회차 수준)

**목표**: AI에게 코드를 만들게 하되, 품질 기준은 내가 정한다

```
갖춰야 할 역량:
├── 플랜 모드 사용법 (Shift+Tab)
├── CLAUDE.md 작성 원칙 (못하는 것만 넣기)
├── AI 코드 리뷰 능력 (잘한 것 확인 + 못한 것 교정)
└── 레이어별 테스트 정책 수립

만들어야 할 것:
├── CLAUDE.md (프로젝트 규칙)
├── 테스트 정책 (도메인: 순수 단위, 서비스: 통합, 컨트롤러: MockMvc)
└── 커밋 메시지 규칙

체크포인트:
□ 엔티티 하나로 도메인→리포지토리→서비스→컨트롤러 전체 사이클을 돌렸다
□ AI가 만든 코드에서 "교정이 필요한 부분"을 3개 이상 발견하고 고쳤다
□ CLAUDE.md에 5개 이하의 규칙을 넣었다 (AI가 못하는 것만)
```

### Level 2: 중급 (2회차 수준)

**목표**: AI를 감싸는 도구를 만들어서 더 잘 일하게 만든다

```
갖춰야 할 역량:
├── 에이전틱 루프의 이해 (컨텍스트 → 액션 → 검증 → 반복)
├── 기본 도구 목록 파악 (Bash, Read, Write, Edit, Glob, Grep, WebSearch 등)
├── 스킬 만들기 (Skill Creator 활용)
├── 서브 에이전트 만들기 (컨텍스트 분리)
└── 컨텍스트 구조 이해 (시스템 프롬프트 + 히스토리 + 도구 목록)

만들어야 할 것:
├── 스킬 2~3개 (프로젝트 생성, 자주 쓰는 프롬프트)
├── 에이전트 1개 (코드 품질 분석)
├── 퍼미션 설정 (Allow 리스트 + Deny 리스트)
└── 스테이터스 라인 (모델명, 브랜치, 컨텍스트 잔량)

체크포인트:
□ "현재 사용 가능한 도구를 알려줘"로 도구 목록을 확인했다
□ 반복 프롬프트를 스킬로 만들었다
□ 코드 분석을 에이전트로 분리해서 컨텍스트를 보호했다
□ /context로 컨텍스트 사용량을 확인하고 관리하고 있다
```

### Level 3: 고급 (3회차 수준)

**목표**: AI와 협업하는 워크플로우를 설계하고, 나만의 하네스를 구축한다

```
갖춰야 할 역량:
├── 워크플로우 4단계 체화 (탐색 → 계획 → 구현 → 커밋)
├── 상황별 도구 선택 (플랜 모드 / Superpowers / Ralph)
├── 멀티 모델 협업 (Claude + Codex + Gemini)
├── 보안 설정 (Deny + 훅 이중 차단)
├── 하네스 개념 이해와 구축
└── 모델 업데이트 시 스킬 재검증

만들어야 할 것:
├── Superpowers 브레인스토밍 워크플로우
├── 멀티 모델 리뷰 스킬 (Codex/Gemini 연동)
├── 보안 훅 (block-dangerous)
├── 대화 기록 저장 훅 (Save Conversation)
├── 레퍼런스 스킬 (최신 기술 변경점, 팀 관례)
└── 나만의 플러그인 (자주 쓰는 스킬/에이전트 묶음)

체크포인트:
□ Superpowers로 프로젝트를 설계하고 Codex/Gemini로 크로스 리뷰했다
□ SSH키, AWS키 등 민감 정보에 대한 Deny + 훅 이중 차단을 설정했다
□ 모델 업데이트 후 기존 스킬의 유효성을 재검증했다
□ 대화 기록이 커밋에 자동 포함되는 워크플로우를 구축했다
```

## 4. 실전 워크플로우 통합 맵

### 프로젝트 생성부터 리뷰까지 — 한 장 정리

```
┌─────────────────────────────────────────────────────────────┐
│ Phase 0. 환경 준비                                           │
│                                                              │
│  □ 설정 리셋 (한 달 주기)                                     │
│  □ 오피셜 플러그인 설치 (선별적으로)                            │
│  □ 보안 설정 (Deny + 훅)                                     │
│  □ 스테이터스 라인 설정                                       │
│  □ 퍼미션 설정 (자주 쓰는 안전한 명령 Allow)                    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ Phase 1. 프로젝트 생성                                       │
│                                                              │
│  도구: 스프링 이니셜라이저 스킬                                │
│  원칙: #3 AI에게 시키고 교정 / #7 선별 설치                    │
│  주의: AI가 직접 만들면 버전 호환 문제 발생                     │
│        → 반드시 이니셜라이저 사용 지시                         │
│  산출물: 기본 프로젝트 + git init                              │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ Phase 2. 가이드라인 빌드업 (초반 투자)                         │
│                                                              │
│  방법: 엔티티 하나로 전체 레이어 관통                          │
│  도구: 플랜 모드                                              │
│  원칙: #3 먼저 시키고 교정 / #4 못하는 것만 CLAUDE.md에         │
│                                                              │
│  사이클:                                                     │
│  도메인 → 리포지토리 → 서비스 → 컨트롤러                      │
```

## 5. AI 교정 패턴 종합 카탈로그

3회 시리즈 전체에서 발견된 "AI가 틀리는 지점"을 통합했습니다.

### 프로젝트 생성 단계

| 패턴 | 증상 | 교정 방법 |
|------|------|-----------|
| 구버전 사용 | Boot 3.x, Java 17 등 학습 데이터 기준 버전 | 버전 명시 + 이니셜라이저 사용 지시 |
| Gradle/Java 호환성 | Gradle 8 + Java 25 → 호환 안 됨 | 이니셜라이저가 검증된 조합 제공 |
| 스프링부트 4 미적응 | Jackson 패키지, 테스트 모듈 변경 인식 못함 | 웹 검색으로 자체 해결 가능. 반복 시 CLAUDE.md에 기록 |

### 코드 생성 단계

| 패턴 | 증상 | 교정 방법 |
|------|------|-----------|
| 필수 항목 검증 누락 | 생성자에서 null 체크 등 검증 없음 | 코드 리뷰 후 보강 요청 |
| 테스트 미생성 | 기능만 만들고 테스트 생략 | "기능 구현 시 테스트도 같이 만들고 실행" 명시 |
| 도메인 테스트에 JPA 투입 | @DataJpaTest, EntityManager 사용 | "도메인은 순수 단위 테스트, JPA 금지" 명시 |
| 서비스 테스트를 Mock으로 | Mockito로 리포지토리 모킹 | "@SpringBootTest + H2 통합 테스트" 명시 |
| 한 번에 너무 많이 생성 | 요청 범위를 넘어서 과도한 코드 생성 | 사이클 범위를 작게 지정, TDD로 쪼개기 |

### 설계 단계

| 패턴 | 증상 | 교정 방법 |
|------|------|-----------|
| 최신 프레임워크 기능 오해 | 스프링 4/7의 새 기능을 잘못 사용 | 멀티 모델 리뷰 (Codex가 잘 잡아냄) |
| 데이터 모델 누락 | 소프트 딜리트인데 deleted_at 없음 | 멀티 모델 리뷰 + 꼼꼼한 사람 리뷰 |
| N+1 쿼리 | 연관 관계 로딩 최적화 없음 | 코드 품질 오디터 → TDD로 수정 |
| 아키텍처 위반 | 컨트롤러에서 리포지토리 직접 주입 | 코드 품질 오디터 → 레이어 규칙 적용 |

## 7. 보안 체크리스트

### 필수 Deny 설정

```
# 민감 파일 읽기 차단
read: ~/.ssh/*          # SSH 키 → 서버 탈취
read: ~/.aws/*          # AWS 크레덴셜 → 요금 폭탄
read: ~/.gnupg/*        # GPG 키

# 환경변수 수정 차단
edit: .env
edit: .env.*

# 위험 명령 차단
bash: rm -rf
bash: curl (상황에 따라)
```

### 훅으로 결정적 차단

> Allow/Deny는 프롬프트 기반 → AI가 가끔 무시함 (3회차에서 공개된 충격적 사실)
> 진짜 위험한 것은 **훅으로 코드 레벨 차단** (결정적, deterministic)

- `block-dangerous` 훅: rm -rf 등 위험 명령 실행 전 차단
- 민감 파일 접근 훅: SSH/AWS/env 파일 접근 시도 시 차단
- 훅은 AI가 무시할 수 없음 → 최종 방어선

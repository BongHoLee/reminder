# 토비의 클로드 코드와 스프링 개발하기 - 강의 1

> 클로드 코드를 이용한 바이브 코딩으로 스프링 애플리케이션(애플 리마인더 클론)을 개발하는 라이브 코딩 강의

---

## 1. 강의 소개 및 개발 철학 [00:17]

안녕하세요. 오랜만에 라이브를 켰는데 오늘은 제가 코딩하는 코딩 라이브가 아니고 오늘 이제 AI가 코딩하는 소위 바이브 코딩이라고 하죠. 입코딩이라고도 하고 말로 하는 코딩, 이걸로 해서 스프링 애플리케이션 개발을 어떻게 할 것인가?

다들 잘 알고 계시겠지만 가장 개발자들이 좋아하는 개발 툴이라고 하는 클로드 코드가 AI 코딩 도구를 사용하는 사람의 45% 정도는 클로드 코드를 쓴다는 조사가 있더라고요.

### 세팅 리셋의 중요성

요즘에 클로드 코드에 확장할 수 있는 포인트가 되게 많죠. 유튜브만 열면 많은 얘기들을 하는데, 이런 것들을 그냥 마구잡이로 막 넣어서 하다 보면 처음엔 좋았다가 모델도 바뀌고 버전 올라가고 그러면 뭔가 좀 이상한 거 같기도 하고, 내가 뭘 어떻게 제어해야 될지 모르겠다. 이런 얘기를 하시는 분들이 제법 있더라고요.

그래서 저는 클로드 코드의 모든 세팅을 기본 설치했을 때 초기 세팅에서 쌓아 갔던 것들, 플러그인도 설치하고 뭔가 작업을 했던 거를 **한 달에 한 번은 리셋을 합니다**. 새로운 모델이 나오거나 뭔가 변화가 생기면 그때 한 번씩 리셋하고, 이전에 했던 것 중에서 내가 확신이 있는 거를 다시 빌드업 하는 거를 매번 하려고 합니다.

---

## 2. 프로젝트 소개: 애플 리마인더 클론 [03:19]

지금 상황은 유저 밑에 `.claude` 폴더를 백업하고 싹 삭제했습니다. 맨땅인 상태에서, 플러그인 하나도 없이 초기화를 했습니다.

개발할 건 **애플의 리마인더 앱** 비슷한 걸 만들어 보려고 합니다. 리마인더는 아이폰에도 있고 맥에도 있고, 리스트도 만들어 놓고 쇼핑 리스트, 회사 업무 관련 체크 리스트 등으로 아주 잘 쓰고 있는데요. 그냥 투두 리스트인데 굉장히 잘 만들어진 거예요.

### 기능 스펙은 AI에게

기본적으로 기능이나 이런 건 별로 고민할 게 없는게, "애플 리마인더 앱"이라고 그러면 AI들이 다 잘 알더라고요. 그래서 상세한 스펙을 주지 않아도 됩니다.

---

## 3. 기술 스택 결정 [05:24]

- **백엔드**: Spring Boot (최신 4.0 버전)
- **프론트엔드**: Next.js 최신 버전 + TypeScript
- **데이터베이스**: H2 (간단한 개발용)
- **빌드**: Gradle (Kotlin DSL)

백엔드만 많이 해 보신 분들은 프론트엔드 개발이 약한데, 리액트나 Next.js 공부하고 쓰시는 분들도 있지만 시간도 많이 걸리고 이쁘게 잘 만들려면 어렵죠. 그래서 프론트엔드는 이렇게 합시다. 백엔드는 스프링부트. 프론트엔드는 넥스트 JS 최신 버전.

스프링에 대해서 어느 정도 자신만의 아키텍처, 코딩할 때 꼭 지켜야 되는 가이드들이 있잖아요. 그런 것들을 AI한테 가이드를 해 주면서 개발을 하면 좋고, 프론트엔드는 잘 모르니까 **그냥 AI한테 맡겨서 진짜 바이브 코딩으로** 해 보겠습니다.

---

## 4. 프로젝트 생성: 플랜 모드와 스프링 이니셜라이저 [09:33]

### 먼저 AI에게 물어보기

새로운 프로젝트를 처음 만들 때, PRD를 만들어라 뭐 스펙을 만들어라 여러 가지 얘기들이 많은데, 맨땅에서 한다 그러면 뭐부터 시작을 해야 될까요?

저는 기본적으로 **플랜 모드를 켜놓고**, 코드를 생성하지 않도록 해 놓은 다음에 먼저 AI가 어떻게 만드려고 하는지 확인합니다.

### AI의 기본 선택 확인 [12:37]

플랜 모드에서 "스프링부트와 JPA, H2를 사용하는 프로젝트를 구성해 줘"라고 하면, AI가 계획을 보여줍니다. 빌드 도구, 자바 버전 등의 선택지를 주는데, 현재 클로드는 학습된 게 **스프링 부트 3.x 버전**입니다. 우리는 4.0을 원하니까 여기서 이미 틀어지죠.

### 스프링 이니셜라이저를 사용하는 이유 [15:42]

AI한테 스프링 부트 프로젝트를 만들어 달라고 하면, 스프링 이니셜라이저를 이용하지 않고 **자기가 직접 만들려고** 해요. 그러다 보면 되게 이상해집니다. 특히 스프링부트 4에서는 Gradle 9을 써야 되고, 자바 25 이상과 호환 문제도 있고요.

그래서 프롬프트에 **"스프링 이니셜라이저를 이용해서"**라는 말을 넣어 주면 AI가 `start.spring.io` API를 호출해서 인텔리제이가 하는 것처럼 작업을 해 줍니다. 우리는 스프링 이니셜라이저를 이용해서 만들면 되니까, 스프링 개발자들이 세팅해 놓은 최선의 걸 가지고 만들면 됩니다.

### 스킬(Skill)로 반복 작업 자동화 [18:49]

프로젝트를 굉장히 많이 만들어서 여러 가지 시도를 해 보다 보면, 만들 때마다 이야기하는 거 귀찮잖아요. 이걸 **스킬로 만들어 놓고** "스프링 프로젝트 만들어 줘"라고 하면 기본 구성을 알아서 하도록 합니다.

> **스킬을 만드는 기준**: 어떤 작업이 **세 번 이상 반복**되면 스킬로 만들어 두세요. 그리고 스킬 만드는 거를 AI가 너무 잘해 줘요. 우리가 직접 프롬프트 만들고 코드 만들지 않아도 됩니다.

## 5. 프로젝트 초기 확인 및 Context Seven [19:49]

### 인텔리제이에서 프로젝트 확인

프로젝트 만들고 나면 인텔리제이 같은 IDE로 들어가서 **AI가 어떻게 코드를 만들었는가**를 확인합니다. 패키지 구조, 라이브러리 구성, 부트 4, 스프링 7 버전 등을 체크하죠.

### Context Seven 대신 웹 검색 [20:50]

예전에는 Context Seven이라는 걸 사람들이 많이 썼는데, AI가 직접 웹 검색하고 페치하는 기능이 들어간 이후로 저는 굳이 그 기능을 쓰지 않습니다. 최신 버전도 잘 올라오지도 않을뿐더러 웹사이트 검색하면 AI가 잘 찾아 주거든요. 게다가 Context Seven MCP는 무겁고 컨텍스트 많이 잡아 먹어요.

## 6. 개발 접근 방식 선택 [30:00]

개발을 어떤 식으로 진행할지 여러 가지 선택지가 있습니다:

### 방법 1: 프롬프트 → 바로 개발
간단한 프로토타입을 써보고 빠르게 만들어 보고 싶다면, "이 기능 만들어 줘"하고 코드 나온 다음에 고치고 고치고 하는 방식.

### 방법 2: 플랜 모드 활용
프롬프트를 넣되 플랜 모드를 거쳐서 우리가 한번 확인을 받는 거죠. AI가 잘 이해를 했는지. 대체로 아주 상세하게 길게 만들지 않아도 AI가 플랜을 상당히 잘 짜 줍니다.

### 방법 3: PRD 기반 개발
PRD.md 같은 걸 만들도록 먼저 요구하고, 이걸 가지고 리뷰하고, 마음에 든다 그러면 이걸 기준으로 개발 시키는 방법.

### 방법 4: SDD(스펙 주도 개발) 스타일
스펙 → 구현 플랜 → 태스크 리스트 → 단계적 개발 순으로 진행하는 방식.

> **어떤 방식이 좋은가?** 그때그때 달라요. 중요한 거는 **이번 단계에 개발 완료할 범위가 어느 정도인가**를 생각해야 됩니다.

### 엔티티 하나부터 시작하는 방법 [33:02]

- 엔티티 하나를 잡고 도메인부터 시작해서 리포지토리, 서비스, 컨트롤러를 만들면서 **내가 원하는 스타일로 개발 가이드를 만들어 나가는** 방식
- 이걸 나중에 반복 사용할 수 있는 **개발 컨벤션 가이드라인**으로 만들어서, 다음 프로젝트부터는 제공해 주는 거죠

## 7. PRD/스펙 작성 [35:05]

저는 플랜보다는 **명시적으로 문서를 남기는 게** 더 좋더라고요. 플랜은 세션이 끝나면 사라지거든요. 오토 메모리가 있어서 어느 정도 기억은 하겠지만요.

애플 리마인더 앱의 웹 버전을 만든다고 하면, 기능이나 이런 거를 굳이 주지 않아도 AI가 잘 알아요. 기능 스펙을 작성하고, 이후 SDD 스타일로 구현 계획을 따로 나눕니다.

### 개발 계획의 구조 [42:27]

AI가 만들어준 개발 계획:
- **페이즈 1**: 가장 단순한 형태 API를 먼저 동작시킨다 → 초기 데이터도 넣어 주고 검증
- **페이즈 2**: 프론트엔드 기본적인 거
- **페이즈 3**: 리마인더 CRUD

> 굉장히 상세하게 쪼갰네요. 좋습니다. 각 페이즈 완료 조건(Acceptance Criteria)을 주면 AI가 검증까지 다 할 수 있어요.

## 8. 도메인 엔티티 개발과 테스트 [51:41]

### 먼저 AI가 만든 코드 확인

리마인더 리스트 도메인 엔티티를 만들라고 하면 AI가 전형적인 Lombok을 이용한 JPA 엔티티를 만듭니다. 잘했네 하고 넘어가면 안 됩니다. 우리가 개발할 때 지켜야 될 기본 규칙들을 빡시게 적용해 보고 넘어가는 게 좋겠죠.

### 테스트에 대한 중요한 원칙 [56:47]

대부분의 AI들은 개발하라 그러면 코드는 만들어 내는데 **테스트를 안 만들어요**. 테스트 만들 준비도 안 해요.

> **핵심 규칙**: "앞으로 기능을 구현하거나 수정할 때 테스트도 같이 만들어 줘. 테스트만 만들고 실행을 안 할 수 있으니까 실행까지 해 줘."

### 도메인 테스트는 순수 단위 테스트 [1:00:58]

AI한테 도메인 테스트를 만들라고 하면 **JPA를 끌어와서** 만들어 버려요. 이러면 우리가 원하는 단위 테스트가 아닌 거죠. 초기에 이걸 잘 잡아야 합니다.

> **가이드**: 도메인 엔티티는 어떤 기술에 의존하지 않는 방식으로 코드를 작성. JPA 같은 걸 사용하지 않도록. 자바 코드로 된 로직만 검증하도록. JPA 기능을 이용하는 부분은 리포지토리 테스트 할 때 넣으면 됩니다.

## 9. CLAUDE.md 관리 전략 [1:04:03]

### 넣어야 할 것과 빼야 할 것

AI한테 문서를 만들어 달라고 하면 AI는 굉장히 장황하게 넣습니다. 그러다 보면 나중에 엄청 길어지고 **성능이 떨어집니다**. 너무 양이 많으면 이 중에서 어떤 것들은 무시해 버리거든요.

> **원칙**: AI가 내가 시키지 않아도 **알아서 잘하는 거는 넣지 않아요**. 예를 들어 "엔티티에 @Entity 어노테이션 붙여라" 같은 건 넣을 필요 없습니다.

넣어야 할 것들:
- AI가 기본적으로 잘못하는 것 (예: 도메인 테스트에 JPA 넣는 것)
- 내가 원하는 특별한 컨벤션
- 참고 문서 (tasks.md 등)

### 세션을 넘어가도 유지되어야 할 것은 남겨둬야

대화 내용은 컨텍스트에 유지되지만, 세션을 빠져나가면 다 까먹어요. 오토 메모리에 좀 기억을 해 준다고는 하지만, **원래 못 했던 거는 남겨 둬야 됩니다**. 빼시면 안 됩니다.

## 10. 서비스 레이어 개발 [1:08:05]

### 서비스 코드 리뷰

AI가 만든 서비스 코드를 확인합니다:
- 생성자 주입 사용 ✓
- 기본적으로 `@Transactional(readOnly = true)` 하고 변경 있는 것만 `@Transactional` 넣기 ✓
- 좋은 관례를 잘 따라가서 했죠

> 우리 팀에서 이 스타일로 안 한다 그러면 바꿔 달라고 하면 됩니다.

### 서비스 테스트 정책 변경 [1:12:06]

AI한테 서비스 테스트를 만들어 달라고 하면 **항상 Mock 테스트를 만들어** 버려요. 리포지토리가 복잡해지면 테스트는 지저분해지고, DB까지 갔다 오지 않기 때문에 나중에 문제가 남기 쉽거든요.

> **내 스타일**: 서비스 테스트부터는 **Spring Boot Test를 이용하고 리포지토리까지** 이용해서, 메모리 DB(H2)를 사용해서 뒷단의 기능을 다 활용하는 방식으로 테스트를 만듭니다. `@Transactional`이니까 다 롤백 테스트가 되니까 DB까지 간다고 하더라도 굉장히 빠릅니다.

### 인터페이스 분리 [1:14:08]

서비스는 하나의 계층이기 때문에, 계층 앞단에는 **인터페이스를 두는 게** 계층 아키텍처에서 요구하는 바이죠. 예전에 인터페이스 타이핑하는 거 귀찮아서 안 만든다 그러는 사람이 있었는데, AI가 만들어 줘요.

- 인터페이스는 `port.input` 패키지에 배치
- 구현 클래스 네이밍: `Impl` 대신 **`Default` 접두사** 사용 (예: `DefaultReminderListService`)

## 11. 외부 명령 승인과 권한 관리 [27:57]

### Accept Edits와 외부 명령

플랜 모드가 끝나면 Accept Edits On이라서 파일 생성/변경은 그냥 다 승낙하는 구조입니다. 하지만 외부 명령을 실행하는 건 매번 확인을 합니다. 프로젝트 내 파일 수정은 스냅샷을 만들어 놓기 때문에 복구가 가능하지만, 외부 명령이나 외부 시스템 연동은 복구가 안 되기 때문이죠.

자주 사용하는 안전한 것들은 유저 레벨 세팅에 미리 Allow 해두면 매번 승인하지 않고 쓸 수 있어요. YOLO 모드(모든 거를 다 허용)도 있는데, 프로덕션 DB를 통째로 날려먹은 사람 얘기도 있긴 합니다.

## 12. 병렬 개발과 워크트리 [1:44:49]

### Git Worktree 활용

병렬로 개발을 진행시킬 때 클론을 여러 개 받아 가지고 하는 방법도 있지만, 로컬 안에서 **Git Worktree**로 분리해서 작업하고 나중에 머지하면 훨씬 편리합니다.

클로드 코드가 이걸 알아서 다 해 줍니다. 시작할 때 `-w` 옵션과 이름만 주면 됩니다:
```
claude -w review
```

폴더를 별도로 설정하고, 작업 끝내고 Ctrl+C로 빠져나가면 AI가 알아서 워크트리 관련 설정을 다 제거해 줍니다.

### 리모트 컨트롤

클로드 코드에 들어간 **리모트 컨트롤** 연결해 두면, 클로드 코드 돌아가는 화면을 폰에서 볼 수 있고 명령도 내릴 수 있어요. 밥 먹으러 가서도 계속 개발할 수 있습니다.

## 15. 코드 리뷰 프로세스 [2:00:23]

어느 정도 개발이 진행되면 리뷰를 빡시게 시킵니다. 클로드 코드한테 리뷰해 달라고 하면 **자기 비판을 아주 잘하더라고요**.

- 주요 이슈: DTO의 검증 없음, Priority Value Object 실패 예외 처리
- **N+1 쿼리** 지적도 잘하고, TDD로 개발하면 N+1 문제를 검증할 테스트를 만들어 주는데 기가 막힙니다
- 이슈 심각도 분류: Critical, Major, Minor, 개선사항

### 리뷰 후 수정

하나씩 하나씩 수정할 수 있게 하거나, 이슈 하나가 해결될 때마다 커밋을 해 달라고 요청하는 방법도 좋습니다. 수정을 하라고 할 때 **테스트 없이 그냥 수정하면 안 됩니다**. 문제가 있었는지 검증도 안 되고, 해결됐는지도 확인이 안 되니까 반드시 검증할 수 있는 테스트를 같이 만들어 달라고 해야 합니다.

클로드 코드 Docs 공식 문서 안에 **어마어마한 내용**이 들어 있어요. 베스트 프랙티스를 포함해서 온갖 기능에 대한 굉장히 좋은 팁들이 들어 있습니다. 단순히 사용 설명만 있는 게 아닙니다. 한국어도 있으니 꾸준히 공부하세요.

> **팁**: 공식 문서 전체를 마크다운으로 다운받아서 하나의 문서로 만든 다음, Gemini 같은 큰 컨텍스트 모델에 던져 놓고 질문하면 좋습니다.

### 기타 유용한 도구 및 팁

- **고스티(Ghostty)**: 터미널 프로그램으로, 속도 빠르고 화면 분할 잘 됨. 클로드 코드 팀이 고스티를 쓴다고 했습니다
- **스테이터스 라인**: 모델명, 폴더, 깃 브랜치, 컨텍스트 잔량 등을 터미널 하단에 표시
- **Whisper Flow**: 음성 입력 도구
- **Claude Usage Bar**: 사용량 확인 도구
- **코덱스와의 협업**: 주로 클로드 코드에서 작업하다가, 코드 리뷰나 마음에 드는 코드가 안 나올 때 코덱스한테도 요청. 단, 맨땅에서부터 코덱스로 시작하면 초반이 너무 피곤함

# 클로드 코드 실전: 워크플로우, 멀티 모델, 하네스 — 학습 가이드

> 강의: 토비의 라이브코딩 3회차 (약 2시간 6분)
> 주제: AI 개발 워크플로우 설계, Superpowers/Ralph 활용, 멀티 모델 협업, 하네스 구축
> 학습 초점: **"코드는 AI가 만들지만, 개발은 사람이 한다" — 워크플로우 설계와 하네스 구축**

---

## Part A. 시청 전 — 프리뷰

> 3회차는 시리즈의 완결편입니다. 1회차(코드 만들기), 2회차(도구 만들기)를 거쳐,
> 이번에는 **"일하는 방식 자체를 설계하는 것"**에 초점을 맞춥니다.

### 이 강의에서 얻을 수 있는 것

- AI 개발의 핵심 워크플로우 4단계 (탐색 → 계획 → 구현 → 커밋)
- 워크플로우 도구 3가지 (플랜 모드 / Superpowers / Ralph)의 사용 분기점
- Superpowers 브레인스토밍의 9단계 실습
- 멀티 모델 협업 (Claude + Codex + Gemini) 실전 워크플로우
- 퍼미션/훅을 이용한 보안 설정
- **하네스(Harness)** 개념과 자기만의 하네스 구축 전략
- 컨텍스트 관리와 대화 기록 저장

### 에이전틱 프로그래밍 핵심 원칙 7가지

| # | 원칙 | 왜? | 적용 시점 |
|---|------|-----|-----------|
| 1 | **워크플로우 4단계를 항상 따르라** | 탐색 → 계획 → 구현 → 커밋. "만들어줘" 한 방은 별로인 결과를 낳음. 잘하는 사람은 1시간 반 중 1시간을 계획에 쓴다 | 모든 개발 작업 시작 시 |
| 2 | **한 사이클의 범위를 조절하라** | AI가 한 번에 너무 많이 만들면 품질이 떨어짐. MVP부터 시작해서 사이클을 작게 돌리고, 확신이 생기면 범위를 넓혀라 | 구현 단계 진입 전 |
| 3 | **도구는 상황에 따라 골라 쓰라** | 플랜 모드(간단/빠름), Superpowers(큰 기능/초기 개발), Ralph(중간 규모/빠른 진행). 모든 상황에 하나만 쓰지 말 것 | 작업 규모를 판단한 후 |
| 4 | **스킬은 워크플로우와 레퍼런스 두 가지 용도로 만들라** | 반복 작업 자동화뿐 아니라, AI가 모르는 지식(최신 기술, 팀 관례)을 저장하는 용도로도 활용 | 새 기술 학습 시, 팀 관례 정리 시 |
| 5 | **멀티 모델로 리뷰하라** | 클로드가 셀프 리뷰해도 놓치는 것을 Codex/Gemini가 잡아냄. 컨센서스 분석으로 의견 정리 | 설계 완료 후, 코드 리뷰 시 |
| 6 | **위험한 것은 Deny + 훅으로 이중 차단하라** | Allow/Deny는 프롬프트 기반이라 AI가 가끔 무시함. 진짜 위험한 것(SSH키, AWS키, rm -rf)은 훅으로 결정적 차단 | 초기 환경 설정 시 |
| 7 | **초반 투자가 퍼포먼스를 결정한다** | 코딩 스타일, 아키텍처, 관례를 초반에 잘 잡아두면 뒤로 갈수록 AI 성능이 폭발적으로 올라감. 안 잡으면 엉망진창 | 프로젝트 시작 첫 1-2일 |

## Part C. 시청 후 — 정리 & 실습

### 워크플로우 도구 선택 가이드

| 상황 | 추천 도구 | 이유 |
|------|-----------|------|
| 간단한 수정, 잘 아는 작업 | **플랜 모드** (Shift+Tab) | 가볍고 빠르고 간단. 플러그인 불필요 |
| 새 프로젝트 시작, 큰 기능 추가 | **Superpowers** `/brainstorming` | 9단계 진행, 명확화 질문, 비주얼 컴패니언, 셀프 리뷰 |
| 중간 규모, "대략 알겠고 빨리 했으면" | **Ralph** | 질문 한 번, PRD 특화, 빠른 진행 |
| 버그 수정 | **플랜 모드** 또는 **Ralph** | 탐색(원인 파악) → 계획(수정 방안) → 구현 사이클을 가볍게 |
| 설계 검증이 중요한 작업 | **Superpowers** + **멀티 모델 리뷰** | Superpowers로 설계 → Codex/Gemini로 크로스 리뷰 |

### 멀티 모델 협업 워크플로우

```
1. Claude Code로 스펙/플랜 작성 (Superpowers 브레인스토밍)
   ↓
2. Codex에게 리뷰 의뢰 → 날카로운 기술적 지적
   ↓
3. Gemini에게도 리뷰 의뢰 → 다른 관점의 피드백
   ↓
4. Claude Code가 컨센서스 분석
   - 셋 다 동의하는 것 → 반드시 반영
   - 둘만 동의하는 것 → 검토 후 판단
   - 의견이 다 다른 것 → Claude에게 최종 결정 위임
   ↓
5. 반영 후 구현 진행
```

### 보안 설정 필수 체크리스트

**Deny (원천 차단):**

```
# 민감 파일 읽기 차단
read: ~/.ssh/*
read: ~/.aws/*
read: ~/.gnupg/*

# 환경변수 파일 수정 차단
edit: .env
edit: .env.*

# 위험한 명령 차단
bash: rm -rf
bash: curl (상황에 따라)
```

**훅 (결정적 차단):**

- `block-dangerous` 훅: rm -rf 등 위험 명령을 코드 레벨에서 차단
- Allow/Deny는 프롬프트 기반 → AI가 무시 가능
- 훅은 코드 기반 → 결정적(deterministic)으로 동작

### 하네스 구축 로드맵

```
[Level 0] 기본 클로드 코드
  ↓  CLAUDE.md 작성 (코딩 규칙, 테스트 정책)
[Level 1] + 메모리
  ↓  반복 작업을 스킬로 변환
[Level 2] + 스킬 (워크플로우 + 레퍼런스)
  ↓  코드 품질 분석 등을 에이전트로 분리
[Level 3] + 에이전트 (컨텍스트 보호)
  ↓  보안 설정 + 자동화 훅
[Level 4] + 훅 (보안 + 자동화)
  ↓  멀티 모델 연동
[Level 5] + 멀티 모델 협업 (리뷰, 토론)
  ↓  대화 기록, 자동 커밋 등
[Level 6] 나만의 하네스 완성
  ↓  모델 업데이트 시 재검증 → 사이클 반복
```

### 나의 프로젝트에 적용하기

**즉시 적용 (오늘):**

- [ ] 보안 설정 확인: SSH키, AWS키, .env 파일 Deny 설정 + 훅 차단
- [ ] 다음 작업부터 4단계 워크플로우(탐색 → 계획 → 구현 → 커밋) 의식적으로 적용
- [ ] 컨텍스트 사용량 확인: 200K~300K 수준에서 끊고 클리어하는 습관

**이번 주 적용:**

- [ ] Superpowers 설치 후 `/brainstorming`으로 아무 프로젝트나 설계해보기
- [ ] 자주 쓰는 기술의 레퍼런스 스킬 1개 만들기 (예: "스프링부트 4 변경점")
- [ ] 퍼미션 정리: 안전한 명령은 Allow, 위험한 것은 Deny + 훅으로 이중 차단

**이번 달 적용:**

- [ ] 멀티 모델 리뷰 워크플로우 구축 (Codex 연동 스킬)

| 회차 | 핵심 주제 | 한 줄 요약 |

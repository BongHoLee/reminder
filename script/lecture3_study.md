# 토비의 클로드 코드와 스프링 개발하기 - 강의 3

> AI 개발 워크플로우(탐색→계획→구현→커밋), 슈퍼파워스/랄프 플러그인 활용, 멀티 모델 협업, 하네스 개념을 다루는 강의

---

## 1. 강의 소개: 워크플로우의 중요성 [00:07]

오늘은 AI를 통해서 개발하는 거에 대해 얘기하겠습니다. 전통적으로 해 오던 방식과 크게 다르진 않지만, 개발하는 사이클이나 거쳐야 되는 작업 등이 미묘하게 다릅니다. 아직은 어떤 방식이 가장 좋다는 게 완전히 정립되진 않았어요.

처음에 "만들어 줘"라고 하면 만들긴 하는데 별로예요. 어떻게 하면 더 효과적으로 AI를 사용해서 개발할 수 있을지 연구하다 보면 결국 **워크플로우**에 대한 얘기로 흘러갑니다.

---

## 2. 터미널 환경: Zellij(시먹스) 소개 [03:10]

고스티에서 **Zellij**라는 터미널 멀티플렉서로 바꿨습니다. 2주 정도 사용했는데 너무 좋습니다.

- 좌측에 **워크스페이스** 개념으로 여러 개 만들어 놓고 이름을 줄 수 있음
- 페인(화면 분할) 관리가 편리
- AI가 작업 완료되면 알림이 자동으로 뜸 (번호로 표시)
- 어느 페인에서 응답 대기 중인지 파란색 테두리로 보여줌
- Running/완료 상태가 표시됨

### 새 도구 학습시키기 [09:15]

AI가 Zellij를 모르면 **웹사이트 주고 학습**시키면 됩니다. 한번 학습하면 잘 하지만, 세션 종료하면 까먹으니까 **스킬로 만들어 두세요**.

---

## 3. 스킬의 두 가지 용도 [10:16]

### 용도 1: 워크플로우 자동화
반복되는 프롬프트를 간단한 명령으로 실행할 수 있게 만드는 것. (예: 스프링 프로젝트 생성)

### 용도 2: 레퍼런스 (지식 저장)
AI가 모르는 것, 또는 우리 회사/팀만의 관례를 스킬에 넣어두는 것.

예시:
- **스프링부트 4에서 달라진 점** → 스킬로 만들어 두면 개발 시 자동 참조
- **카프카 사용법** → 웹사이트 학습시킨 후 스킬로 저장
- **팀 코딩 관례** → 스킬로 공유

> 유명한 스킬들은 범용적이지만, **자기만의 스킬**을 잘 만들어 두시는 게 퍼포먼스를 올리는 데 되게 좋습니다.

### 주요 플러그인

처음 시작하시는 분은 아직 쓰지 마세요. 아무것도 모른 채로 깔면 뭔가 잘 되는 것 같은 느낌으로 만들어진 거라, 본격적으로 스킬을 이용해서 워크플로우를 만든 다음에 한번 살펴보시면 괜찮습니다.

## 5. 핵심 워크플로우: 4단계 사이클 [22:36]

### 클로드 코드 공식 문서의 모범 사례를 반드시 읽으세요

클로드 코드 팀이 권장하는 **AI 개발 작업 흐름 4단계**:

1. **탐색(Explore)** - 현재 프로젝트 분석, 코드 파악
2. **계획(Plan)** - 어떻게 만들지 설계, 스펙 작성
3. **구현(Implement)** - 실제 코딩
4. **커밋(Commit)** - 작업 완료, 검증

> 잘하시는 분들은 1시간 반 개발한다면 **1시간 동안 플랜만 짜고 30분 동안 코드를 뽑아낸다**고 합니다. 준비 단계를 충분히 가지지 않으면 원하지 않는 결과가 나올 가능성이 매우 높습니다.

### 이 사이클은 모든 작업에 적용

- 새 기능 추가할 때
- 세세한 기능 변경할 때
- 버그 수정할 때도 (탐색 → 원인 파악 → 수정 계획 → 구현)

## 6. 워크플로우 도구 3가지 [30:45]

### 도구 1: 플랜 모드 (가볍고 빠르고 간단)
- 아무 플러그인 없이 사용 가능
- Shift+Tab으로 전환
- 간단한 수정, 잘 아는 작업에 적합

### 도구 2: Superpowers (큰 기능, 초기 개발)
- **9단계**에 걸쳐 진행: 탐색 → 명확화 질문 → 설계 → 리뷰 → 구현 계획 → ...
- 명확화 질문을 통해 구체화 (목적, 규모, 기술 스택, DB, 인증 등)
- **여러 접근법을 제안**하고 선택하게 함 (추천 이유도 설명)
- **비주얼 컴패니언** - 웹 브라우저에서 아키텍처 다이어그램, 데이터 모델 등을 시각적으로 보여줌
- 매 단계에서 **셀프 리뷰** 진행

### 도구 3: Ralph (중간 규모, 빠른 진행)
- 질문은 딱 한 번 (여러 개를 한꺼번에)
- PRD 만드는 데 특화
- Superpowers보다 빠름
- "대략 알겠고 빨리 했으면 좋겠다" 싶을 때 사용

## 7. Superpowers 브레인스토밍 실습 [51:12]

### 새 프로젝트 시작하기

`/brainstorming` 스킬을 호출하고 "URL 쇼트너 + 분석 기능, 스프링부트로 개발"이라고 하면:

1. 프로젝트 목적 질문 (학습용? 실제 서비스? 포트폴리오?)
2. 사용 규모 질문 (개인? 팀? SaaS?)
3. 기능 범위 질문 (분석 수준, 인증 방식 등)
4. 기술 접근법 제안 (3가지 옵션 + 추천 + 이유)
5. 아키텍처 다이어그램 (비주얼 컴패니언)
6. 데이터 모델 설계
7. API 설계
8. 셀프 리뷰
9. 구현 계획 → 실행

> 처음에 아이디어가 별로 없을 때도 쓸 수 있고, 이미 개발 중인데 새로운 기능을 넣거나 주요한 리팩토링할 때도 괜찮습니다.

## 8. 멀티 모델 협업 (코덱스 + 제미나이) [1:17:01]

### 설계 리뷰에 멀티 모델 활용

1. 클로드 코드가 스펙/플랜 작성
2. **코덱스에게 리뷰** 요청 → 날카로운 지적 (예: "스프링 4 기능을 오해했다", "N+1 문제", "소프트 딜리트인데 deleted_at 없다")
3. **제미나이에게도 리뷰** 요청
4. 클로드 코드가 **컨센서스 분석** - 셋의 의견이 일치하는 부분과 다른 부분 정리
5. 최종 결정은 클로드 코드에게 맡김

### Zellij를 활용한 멀티 모델 실행 [1:19:03]

Zellij의 페인 분할 기능으로 코덱스/제미나이를 각각 별도 페인에 띄우고, **시먹스의 메시지 전송 기능**을 이용해 각 페인에 작업을 보내고 결과를 파일로 받아옴.

## 9. 보안: 퍼미션과 훅 [1:12:49]

### 퍼미션 설정 (Allow / Deny)

**Allow**: 자주 쓰는 안전한 명령을 사전 등록
```
bash: gradle build → 항상 허용
bash: git commit → 항상 허용
```

**Deny (필수)**: 위험한 것은 원천 차단
- `read ~/.ssh/*` - SSH 키 읽기 금지
- `read ~/.aws/*` - AWS 크레덴셜 읽기 금지
- `edit .env` - 환경변수 파일 수정 금지
- `bash: rm -rf` - 위험한 삭제 명령 금지
- `bash: curl` (상황에 따라)

> SSH 키 털리면 서버 다 털리고, AWS API 키 유출되면 다음 달에 요금 3만 달러 나올 수 있습니다.

### 훅(Hook)으로 확실한 차단 [1:40:33]

Allow/Deny는 프롬프트로 날아가는 거라서 **AI가 가끔 무시**합니다. 진짜 위험한 건 **훅**으로 차단하세요. 코드로 동작하므로 결정적(deterministic)입니다.

## 10. 하네스(Harness) 개념 [1:44:39]

### 하네스란?

클로드 코드 = AI 모델을 둘러싸고 있는 **하네스**. 모델만으로는 코딩을 할 수 없기 때문에 도구(Bash, Read, Write 등)를 제공하여 모델이 우리가 원하는 일을 할 수 있게 만든 것.

하지만 클로드 코드 자체만으로는 우리 프로젝트에 부족한 게 있으니까, 스킬/에이전트/훅 등으로 **확장**하는 것 = **나만의 하네스를 만드는 것**.

> 스킬 = 하네스는 아닙니다. 스킬들이 모여서 하네스가 될 수 있는 거죠. 스프링 프레임워크 위에 여러분만의 프레임워크를 만드는 것과 비슷합니다.

### 하네스 관리의 어려움 [1:55:01]

모델이 버전업되면 기존 하네스가 쓸모없어질 수 있습니다. 모델이 바뀔 때마다 **이밸루에이션(검증)**을 다시 해야 합니다. Skill Creator의 최신 버전에 이밸루에이션 기능이 들어간 이유이기도 합니다.

## 11. 컨텍스트 관리 [53:15]

### 1M 컨텍스트 시대

컨텍스트가 200K에서 1M으로 올라온 건 축복이지만, **1M까지 다 채우지 마세요**.

> 저는 웬만하면 200K~300K 레벨에서 끊고 클리어합니다. 이후 새 세션에서 이어갈 수 있도록 **문서가 충분히 만들어지게** 합니다.

컨텍스트가 커지면 앞에서 했던 모든 대화가 뒤의 간단한 요청에도 함께 날아가서, AI가 **정확히 뭘 해야 할지 집중을 못합니다**.

## 12. 대화 기록 저장 (Save Conversation) [2:00:10]

### 왜 필요한가?

AI가 100% 코드를 만들어 주는 시대에, **코드만 공유하는 게 충분한가?** 코드 리뷰할 때 "왜 이렇게 만들었느냐"고 물으면 "AI가 만들어서 모르겠고요, AI한테 물어볼게요" 하는 상황이 생깁니다.

### 제가 만든 방식

커밋 전에 자동으로 실행되는 훅을 걸어서, **AI와 나눈 대화 요약 + 변경된 파일 목록 + 사용한 도구**를 기록으로 남깁니다. PR에 포함시키면 리뷰어가 개발 맥락을 이해할 수 있습니다.

## 13. 핵심 정리 [1:58:08]

### AI 시대에 개발자가 해야 할 것

1. **워크플로우 사이클의 범위 조정**을 잘하세요. 한 번에 너무 많이 만들지 않기
2. **여전히 개발 기술을 알아야** 합니다. 모르면 AI의 실수를 잡을 수 없음
3. AI가 모르는 걸 해 주면 **여러분이 공부하세요**
4. **초반 투자가 중요** - 코딩 스타일, 아키텍처, 관례를 초반에 잘 잡으면 뒤로 갈수록 퍼포먼스가 폭발적으로 올라감

### 코드는 AI가 만들지만, 개발은 사람이 한다

> 클로드 코드 팀도 100% 클로드 코드로 만듭니다. 충분히 좋은 스킬을 만들어 두고, 좋은 하네스를 만들어 두고, 사람이 잘 지시하고, 필요한 부분은 꼼꼼하게 리뷰하면 코드 자체를 만드는 거는 AI가 다 할 수 있어요. **근데 개발은 AI가 해 주는 거 아닙니다. 개발은 사람이 하는 거예요.**
